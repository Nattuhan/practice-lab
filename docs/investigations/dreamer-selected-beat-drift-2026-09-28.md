# 完全感覚Dreamer ライブの選択区間で拍がずれる問題

## 再現と観測

利用者がアプリで選択した約3:04〜3:32では、表示は190 BPMだが、保存結果の拍列が約190.28〜193.75秒で速くなり、約207.82〜211.77秒では約0.235秒間隔へ変わる。前後の約0.316秒間隔と異なり、クリックの位相もずれる。

元WAVのドラム音源でアタックを調べると、後半の異常区間でも約0.316秒の拍に対応する八分位置への一致がほぼ全数だった。約0.235秒を拍として読む根拠は弱い。前半も、両側の安定した拍をつないだ11拍の格子を音源が支持する。

現行の `_dominant_grid_spans` は前半を候補として検出したが、後半の候補は音の八分位置が元の格子と誤検出拍の細分位置の両方に近く、既存の「誤検出より明確に良い」という条件では補修できなかった。密なドラムのアタックでは両方の細分位置へある程度合うので、この差だけでは区別できない。

## 共通処理

両側の安定した拍から測った格子について、候補を短い窓に分けて元音源の八分位置を確認する。誤検出拍そのものへアタックが明確に合う場合は真のテンポ変化として維持する。曲名、ID、正解時刻やBPMは実行時に使用しない。最初の実装案は真のテンポ変化の合成例を誤補正したため、その対照例を回帰テストに追加してから判定を厳しくした。

元WAVからCPUでモデル推論をやり直すと、保存済み結果とは小節頭の位相や曲全体の拍数が異なり、全体で1032拍・258小節になった。従来の候補検出は全拍の格子一致率が80%未満という理由でこの選択範囲を丸ごと除外した。長く安定した拍の列が残る場合はその全体比率だけで除外せず、拍そのものの安定列を候補の両側の根拠として使うようにした。新規推論の拍列にも後処理を再適用すると、190.91〜193.14秒の7間隔と203.25〜211.13秒の25間隔を元の周期で修復し、選択範囲内で再適用しても変化しない。保存結果では190.28〜193.75秒と202.61〜211.77秒が音源に支持された修復範囲になる。

新規推論の曲全体は保存中の解析結果と大きく異なるため、選択範囲以外を未検証のまま置き換えない。元音源を使う共通後処理が両方の入力で成功することを確認し、既存セッションにはそのセッションの拍列から得た修復結果だけを適用する。

既存セッションの `data/results` と `public/results` を `data/work/repair-backups/VMD0hp8Po3o-selected-20260928-223552` に退避し、元音源に基づく共通後処理の結果を両方へ保存した。読み戻した両方は190 BPM、983拍、246小節、2つの修復区間で一致する。再適用しても拍列は変わらない。Python全体330件と4サブテストが成功した。

画面での反映確認に進んだ時点でMacがロックされ、アプリのメモリ上の旧拍列を読み直せなかった。したがって、起動中の画面表示と実際のクリックは未確認。インストール済み通常版の解析ランタイムも旧版で、アプリ内再解析による再発余地は残る。
