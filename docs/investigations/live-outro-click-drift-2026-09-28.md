# ライブ映像の終盤に誤った一定拍を補完した問題

## 症状と観測

報告された「The Beginning」ライブ映像の終盤は、表示BPMが182で、クリックが音源から半拍程度ずれる。曲名、時刻、数値は再現記録だけに使い、実行時の条件には使わない。

- 保存済み結果では、拍間隔が約0.330秒で安定した部分の後、258.03→258.49秒に0.46秒の間隔がある。
- `audioTimingRepair.outro` は258.49秒から304.644秒まで140間隔を補完していた。終盤の約46秒の拍はモデルの検出ではなく、単一の起点から外挿した結果だった。
- 元WAVのこの部分では、短い窓ごとに抽出したアタックが補完格子と一致しない。258.49〜305.04秒の231アタックでは、強度加重の八分位置一致率は約44.5%、四分位置一致率は約18.7%だった。補完を許可する既存基準の65%、20%に達していない。
- 同じ区間は音がほぼ途切れず、拍の半分の長さで測ったRMSの活動率が約99.3%、隣接フレームの変化率が約6.6%だった。このため「保持音・フェード」と判定され、アタックの一致検査を飛ばしていた。

従来の修正は、検出済み拍の局所的な揺れ、拍抜け、BPMの半分・倍の選択を対象にしていた。今回の問題は、それとは別の終端補完経路にあった。既存の終端テストは無音、位相違い、テンポ違いを含んだが、音量が連続して滑らかなライブ録音と同時に拍が不一致になる条件を含んでいなかった。

## 共通処理の変更

`_missing_outro` では、音量の連続性があっても十分なアタックが得られる場合は必ず拍位置を検証する。アタックが疎な保持音だけ、連続音として既存の終端補完を許す。保持音のフレーム境界から生じる微小な偽アタックは、同じ終端区間の音量に対する相対強度で除外する。曲ID、特定時刻、正解BPMを参照しない。

## 検証と範囲

- 元WAVと、保存済み補完情報から補完前の拍列を読み取り専用で復元した入力では、修正後に終端補完が行われず、最後の検出拍は258.49秒となった。
- 保存済みの解析結果や補正記録を入力せず、元WAVからCPUで音源分離・モデル推論を含めて独立再解析した。182 BPM、848拍、212小節となり、`audioTimingRepair.outro` は付かなかった。従来の保存結果は182 BPM、924拍、231小節で、末尾140間隔が誤補完だった。
- 独立再解析のモデル拍は258秒付近から遅くなり、270〜305秒の間隔は約0.59〜0.79秒だった。したがって、終盤を182 BPMの一定間隔と決めつけることは音源にもモデル結果にも反する。終盤の拍全体の音楽的正解性までは確認できていない。
- 連続して大きな音量のまま位相が異なるアタックへ変わる合成音源を、異なるBPM・開始位置で回帰テストに追加した。正しい一定拍の終盤と保持音のフェードを補完する既存テストも維持した。
- 関連テスト54件、Python全体307件と4サブテストが成功した。
- BPM値は録音全体に一つだけ記録する仕様である。拍を確信できない終盤にクリックを作らない修正であり、自由テンポの終盤に新しい拍を推定する機能ではない。

## 保存済みセッションと配布状態

元の `data/results` と `public/results` を、アプリの `data/work/repair-backups/h1PN7LEH2Vs-outro-20260928-201946` に退避した。独立再解析の解析項目を両方の結果へ反映し、曲名、ID、取得元、アセット、最終閲覧時刻を保持した。読み戻した双方は182 BPM、848拍、212小節、終端補完なしで一致する。起動中のアプリで曲を読み直し、212小節と表示されることを確認した。これは保存結果への適用であり、生成処理の修正とは別である。

ソースの解析処理だけを変更した。インストール済みの通常版アプリ・解析ランタイムの更新、リリース公開、R2同期は実施していない。そのため通常版でこの曲を再解析すると、配布済みの旧処理によって問題が再発する可能性が残る。
