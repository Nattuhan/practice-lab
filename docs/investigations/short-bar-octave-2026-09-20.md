# 倍テンポ補正で短い小節の頭が失われる問題

## 原因

「青と夏」の約46秒で、元検出は半テンポ92 BPM。43.400〜46.630秒の
区間は音源検証で低速側5拍と判定される。拍欠落の修復で小節を数え直し、
その後184 BPMへ倍化する処理も先頭から一律4拍ずつにしていたため、
検出済みの46.630秒の小節頭が消え、以後の読み上げが2拍ずれた。

## 共通処理の変更

音源検証済みの修復区間が低速側で奇数拍を含み、音源全体のアクセントから
倍テンポが支持される場合は、修復区間右端の小節頭を保持して数え直す。
最終テンポでの偶数拍位相と拍列への一致も必要とする。
結果として4拍小節の余りは2拍小節となり、クリック間隔は変えない。
曲ID、曲名、固定時刻の例外は実装に含めない。

併せて、追加解析ランタイムが起動時に読み込んだ旧practice_labパッケージを
使い続ける問題を修正。sys.pathの追加だけでは既読パッケージは切り替わらない。
解析エントリーでアプリ側のパッケージを優先し、後処理モジュールを読み直す。
重いモデル依存関係と共有追加ランタイム本体は変更しない。

## 検証

- 保存済み音声と分離音源からモデルを再実行。保存済み拍列・補正データは入力しない。
- 元検出92 BPM、小節頭43.400 / 46.630 / 49.230秒を再現。
- 修正後184 BPM。44.692〜45.984秒は4拍、45.984〜46.630秒は2拍、
  46.630〜47.930秒は4拍。以後も4拍で継続することを確認。
- 実際のフロントのbeatCountsで `1,2,3,4 → 1,2 → 1,2,3,4` を確認。
- 異なる3テンポ・開始位置の合成音源で短い小節の保持を検証。
- 古いパッケージが事前ロードされた条件の回帰テストと、実際の追加ランタイムで
  アプリ側の後処理関数がロードされることを確認。
- Python全体302件とsubtest4件が成功。その後追加したランタイム回帰テストを含む
  関連36件も成功。フロントunit、E2E46件成功。

保存済み対象曲には、再検出した拍列から生成した結果を反映。
セクション名・時刻は保持し、小節番号を更新。元データはローカル作業領域へバックアップ。
Dev版を更新し、通常版の署名・自動更新条件を維持。公開・R2同期は行わない。

この検証は実測アンカーが残る今回の条件を対象とする。元モデルが変拍子の境界を
検出できない任意の音源まで、正確な拍子推定を保証するものではない。
