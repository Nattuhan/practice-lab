# じぶんROCK ライブの選択区間でクリックが遅れる問題

## 再現と原因

利用者がアプリ上で選択した約2:17〜2:39は、保存結果では167 BPMと表示される。しかし拍列は約139.5〜150.2秒だけ約0.52〜0.57秒間隔になり、前後の約0.36秒間隔と一致しない。モデルがこの間のリズムを約3:2の別の拍として追っている。表示BPMを保持するだけではクリックの拍列は維持されない。

前回の終盤修正で、信頼できる小節頭の間が32拍を超える候補を検証前に除外していた。今回は両側に安定した拍があり、139.12〜151.40秒は元の拍間隔で34拍に相当するため、この条件で音源検証自体を飛ばしていた。曲名・時刻は再現記録であり、実行時には使用しない。

元WAVのこの区間では、前後の拍から延長した元の八分位置へのアタックの一致が約70.8%で、遅くなった検出拍への四分位置一致は約27.5%だった。元の拍格子へ戻すと、アタックの八分位置誤差は遅い検出拍の細分位置より平均で約0.072拍小さくなる。中低域のスペクトル変化も、元の拍位置が半拍ずらした位置より概ね強い。これらは一定の167 BPMを維持する根拠である。

## 共通処理

安定拍の両側に挟まれた長い候補も、先行する候補と混ぜずに音源検証する。モデルが単純な整数・分数比のリズムを拍として追った場合は、候補全体の格子一致率だけでは排除せず、両側の安定した拍と音源アタックが元の細分格子を支持するか確かめる。連続性だけを手掛かりにする補修には48拍の上限を残す。音源自体が実際に遅い拍を刻む場合は修復しない。

さらに、保存済み結果では約3:2の比率判定を通っても、元WAVからの新規モデル推論では数ミリ秒の拍時刻差によって通らないことを確認した。整数・分数比との距離を絶対値で測ると速い側ほど許容割合が小さくなるため、比率に対する相対誤差へ変更した。この変更後、元WAVから再推論した結果を共通の後処理へ通すと、167 BPM、618拍、155小節となり、139〜151秒の拍間隔中央値は約0.361秒、最大約0.362秒だった。再適用しても変化しない。

異なるBPM・開始位置と検出時刻の揺れで、約3:2の誤追跡と本当のテンポ変化を対にした回帰テストを追加した。変更前後の処理をローカルにある他の音源結果へ読み取り専用で適用し、この変更が新たに補修したのは報告曲の該当区間だけと確認した。

元のローカル保存結果を `data/work/repair-backups/fRPu7otdBQQ-tempo-20260928-215543` に退避し、元WAVの新規推論結果を `data/results` と `public/results` に反映した。両方を読み戻して167 BPM、618拍、155小節を確認した。起動中のアプリは古い拍列をメモリに保持している可能性があるため、画面操作で選択範囲を動かさず、曲の再読み込みは利用者に案内する。インストール済みアプリの解析ランタイムは未更新で、アプリから再解析すると旧処理が出る可能性が残る。
