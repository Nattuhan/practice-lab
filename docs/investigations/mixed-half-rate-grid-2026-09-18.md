# 曲中の長区間だけ拍が半分になる解析の修正

## 再現と原因

報告対象は「The Beginning」。以下の曲名、時刻、拍数は調査記録であり、実行時の条件や補正値には使用しない。

- 保存結果の表示は182 BPMだったが、拍列は617拍・155小節だった。約0〜78秒と208〜277秒では拍間隔が約0.66秒、中央区間では約0.33秒になっていた。
- 元WAVからの再解析でもこの混在を複数回確認した。全曲の中央値は約0.33秒なので、全体を対象とするテンポの倍・半分判定では修復対象にならない。
- 既存の音源検証は一般的な拍抜けや位相ずれを対象とし、長区間にわたって「支配的な拍周期の2倍」が安定して並ぶ場合を十分に扱えていなかった。
- 問題区間の強いアタックは、検出済みの疎な拍列より、曲内の支配的な約0.33秒格子へ一貫して近かった。このため本当のハーフタイム演奏ではなく、検出器が一拍おきに落とした結果と判断した。

## 共通処理の変更

`practice_lab/audio_timing.py` の支配的な拍格子による修復に、長い半レート区間の検証を追加した。曲名、曲ID、絶対時刻、正解BPMは参照しない。

1. 区間内の検出拍間隔の90%以上が支配的周期の2倍で、十分な長さがある場合だけ候補にする。
2. 最大16拍ごとの全窓で元音源の強いアタックを抽出する。各窓で6個以上のアタックを要求する。
3. 強度加重した距離で、検出済みの疎な拍列と支配的な全拍格子を比較する。疎な拍列への一致が悪く、全拍格子への一致が良く、両者の差も明確な場合だけ修復する。
4. 本当のハーフタイム区間では強いアタックが既存の疎な拍に近いため、比較条件を満たさず保持される。
5. 既存と同じ区間再構築を使い、小節頭とセクションも拍列に合わせて更新する。

## 検証

- 再現した182 BPM・617拍の保存結果と元WAVを入力すると、182 BPMを維持したまま833拍・209小節へ修復した。自動抽出された修復区間は2.71〜77.88秒と208.44〜276.99秒。再適用では変化しない。
- 異なる周期0.33、0.49、0.68秒と異なる開始位置の合成音源で、曲頭・曲末側の長い半レート区間を復元した。
- 同じ拍列でも、外側区間の元音源アタックが本当に半レートの場合は変更しないことを確認した。既存のテンポ変化、無音、位相違い、加速などの非対象テストも維持した。
- 修正版で元WAVから音源分離・モデル推論を含む独立再解析をCPUで実行した。この実行ではモデルが最初から182 BPM・840拍・208小節を返し、0〜278秒の全区間で拍間隔は0.33秒、0.5秒超は0件だった。モデル出力には揺れがあるため、再現した不良出力を使う検証と独立再解析の両方を成立条件とした。
- Pythonテスト283件と4件のサブテストが成功した。

## 反映範囲

ローカルの保存結果と再生用コピーへ共通処理を適用し、182 BPM・833拍・209小節で読み戻した。変更前の結果、マニフェスト、再生用コピーはApplication Support配下の作業領域へ退避した。

ソース実装とローカル保存結果に加え、このMacの追加解析ランタイムへ反映した。バージョン変更、GitHub Release公開、R2同期は実施していない。

通常版アプリ本体は置き換えず、Developer ID署名、署名の整合性、起動時更新チェック、自動更新可能の状態を維持した。修正版から作成したランタイムは内包モジュール検査と解析コマンド起動を通し、凍結ランタイム単体でも再現した不良拍列を182 BPM・833拍・209小節へ修復した。インストール後の実行ファイルはビルド品とSHA-256が一致し、旧ランタイムはApplication Support配下へ退避した。
