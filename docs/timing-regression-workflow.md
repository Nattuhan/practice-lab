# 拍・BPM・クリック不具合の回帰確認

単体テストで補正関数が正しく動いても、アプリに同梱した解析経路ではモデル出力が異なることがある。保存済み結果の表示だけでは新しいコードの効果を確認できない。拍・BPM・クリックの修正は、次の順に検証する。

1. 報告された症状を、対象区間・期待するBPM・拍間隔・クリックを止めてよい位置として記録する。元音源と修正前の保存結果を退避する。曲名や固定時刻は検証記録にだけ置き、解析コードへ渡さない。
2. 元音源とモデル出力を使い、失敗がモデルの拍列、倍テンポ判定、音源との照合、保存、再生のどこで生じるか測る。原因未確認の閾値変更は行わない。
3. 共通処理を修正し、報告例に加え、異なるテンポ・開始位置・真のテンポ変更など変更してはいけない例でテストする。表示BPMだけでなく拍間隔の分布と終端も検査する。
4. 開発版をビルドし、変更した解析モジュールがビルド内に含まれることをソースとのハッシュ比較などで確認する。通常版アプリとバージョンはローカル検証だけのために変更しない。
5. **開発版アプリから元音源を再解析する直前**に開始マーカーを作る。アプリの処理一覧で再解析ジョブの「完了」を確認した後、保存結果に対して下の検証コマンドを実行する。更新時刻の確認だけでは、画面を開いた際のメタデータ更新と再解析を区別できないため、ジョブ完了確認を省略しない。
6. 曲画面でBPM・小節数・処理完了を確認し、問題の区間を実際に再生してクリックと音源を聴く。数値検査だけで聴感上の拍の位相は保証できない。
7. 実測値、失敗した条件、未解決のずれを調査記録へ残す。コード、保存済みデータ、開発版、通常版への反映状況を分けて報告する。期待条件を満たさない場合は完了扱いにしない。

開始マーカーと検証の例。`RESULT` は対象の保存結果、`MARKER` は作業用ファイルを指す。期待値はその事例の観測と利用者の指摘から決め、解析処理には使用しない。

```bash
RESULT="/path/to/data/results/session.json"
MARKER="/tmp/practice-lab-analysis-start"
python scripts/verify_timing_result.py --mark-start "$MARKER"
# ここで開発版アプリから元音源を再解析し、処理完了を確認する。
python scripts/verify_timing_result.py \
  --result "$RESULT" --fresh-after "$MARKER" \
  --bpm 160 --window 60 250 --last-beat-between 279 279.5
```

検証コマンドはBPM、選択区間の各拍間隔が期待周期に合う割合、最後の拍、結果ファイルの更新時刻を調べ、条件を外れると終了コード1を返す。`--window` は安定した拍を確認したい区間を指定する。`--last-beat-between` は早く止まり過ぎる誤判定と遅いクリックの両方を検出するため、上限・下限を指定する。必要なら `--bpm-tolerance`、`--interval-tolerance`、`--minimum-grid-coverage` を調整し、その理由を調査記録へ残す。

DECISIONライブ音源の現行開発版は160 BPMで、約60〜250秒の拍間隔は安定している。一方、クリックの最終拍は283.92秒で、かき回し開始の目安4:39（279秒）より約5秒遅い。上記の終端条件では**失敗する**。この差が残る間は、かき回し開始から正しく止まるという検証は通っていない。
